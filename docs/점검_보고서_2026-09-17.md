## 4. 서비스 고도화 방향

### 1단계: 믿고 저장하고 공유하는 견적

인증·PIN·규격 해석·저장 재시도·가격 적용 정책·공유용 데이터·오류 화면을 먼저 정리한다. 이 단계의 완료 기준은 “예쁜 화면”이 아니라 다음과 같은 실제 업무 결과다.

- 관리자 데이터는 미인증 접근에서 반환되지 않는다.
- 같은 초안을 저장 재시도해도 견적이 한 건만 생긴다.
- 단가 등록→규격 선택→음성 해석→문서에서 W/D/H가 일치한다.
- 이전 견적 복사 시 적용 가격이 분명하고, 가격 변경이 조용히 지나가지 않는다.
- 없는 견적·만료·서버 거절이 0원 문서나 성공 메시지로 나타나지 않는다.
- 고객 응답에는 숨기기로 한 내부 마진이 포함되지 않는다.

### 2단계: 고객이 문의하고 견적을 이해하는 흐름

랜딩→현장 조건이 채워진 문의→접수 확인→모바일 견적→현재 견적에 대한 상담으로 연결한다. 문의에는 랙을 모르는 고객을 위한 “잘 모르겠어요” 선택과 필요한 정보의 짧은 설명을 둔다. 연락 예상 시간은 실제 운영 가능 범위를 확인한 뒤 설정한다. 허구의 접수번호·보장 시간을 넣지 않는다.

사례 데이터는 사진·지역·업종·랙 종류·한 줄 작업 내용·원문 링크·공개 허용 여부를 중심으로 정리한다. 사진 업로드, 관리자 사례, 공개 사례 사이의 연결을 분명히 하고 RSS는 보조 수단으로 사용한다. 전체 리뉴얼 없이 기존 정적 페이지와 Sheets 안에서도 진행 가능한 범위다.

### 3단계: 두 사용자의 반복 업무 줄이기

‘견적 / 업무함 / 관리’ 3탭 통합안을 권한다. 업무함은 미처리 문의, 후속 연락이 필요한 견적, 최근 견적을 모은다. 시공 사례 발송 빈도가 높다면 사례 탭을 유지하는 4탭안도 비교할 수 있다. 확정 전에 실제 사용 빈도를 확인한다.

상태는 문의·견적 간 연결을 중심으로 단순하게 유지한다. 새 문의 건수와 읽음 표시의 의미를 구분하고, 기기별 로컬 값만으로 판단하는 배지를 정리한다. 관리자 사진 업로드에는 압축·개수 제한·장별 결과·실패 파일 재시도를 제공한다. 자동 동기화 큐나 복잡한 CRM을 바로 추가할 필요는 없다.

### 4단계: AI와 자동화는 확인 가능한 보조에 집중

- 말로 담기: 실제 단가표와 정확 매칭, 규격 복창, 사용자의 최종 확인을 유지한다. 로컬 파서가 동작한다는 사실과 실기기의 음성 인식·오프라인 지원은 별도로 검증한다.
- 고객 문의: 상담 전에 확인할 질문과 빠진 정보만 요약한다.
- 사진 분석: 보이는 제약 후보와 추가 촬영 질문을 제공하고, 하중·최종 수량·정확 규격의 근거로 사용하지 않는다.
- 카톡 문구: 고객·금액·규격·유효기간은 구조화된 데이터로 고정한다.
- 후기 초안: 완료 여부·실제 시공일·확인된 자재 특성만 사용한다. 무료·보장·시공 사실을 고정 템플릿이 만들어내지 않도록 한다.

효과는 실제 두 사용자가 같은 과제를 수행하며 측정한다. 새 견적 작성 시간, 기존 견적 복사 후 수정 시간, 잘못 선택한 규격/단가, 놓친 문의, 저장 재시도 시 중복 여부, 고객의 견적 이해도를 확인한다. 개선 시간을 미리 성과 수치로 홍보하지 않는다.

## 5. 검증 결과와 유지보수 방향

- `node tools/verify-reskin.mjs`: 통과.
- `test/*.mjs` 10개 파일: 모두 통과.
- `test/calc.test.html`: 16 passed, 0 failed. 다만 실제 `js/calc.js`를 읽지 않고 별도 `calculateEstimate()`를 검사하므로 현재 견적 계산 전체를 보증하지 않는다.
- 추가 실제 소스 재현: PIN 변경 실패 은폐, 저장 재시도 ID 변경, 옛 단가 통과, 규격 축 교차를 확인했다.
- 브라우저 재현: 이미지 저장 버튼 잘림, 없는 견적의 0원 렌더링, 전화 형식 미검사, 생성 초안의 금지 문구를 확인했다.

현 검증 스크립트는 main 대비 기존 요소·문구·핸들러 보존과 일부 파일 불변을 주로 검사한다. 새 랜딩·생성 문자열·API 실패 경로·실제 저장 왕복의 품질을 모두 검사하는 도구는 아니다. 기존 불변 조건이 금지 문구 제거나 백엔드 수정과 충돌하는 부분은 향후 구현 범위와 함께 명시적으로 조정해야 한다.

추가할 검증은 위 재현 시나리오처럼 실제 업무 실패를 잡는 항목에 집중한다. 장기적으로는 CDN 런타임 스타일 생성과 여러 HTML에 흩어진 설정을 정리하고, 버전 값을 하나의 배포 절차에서 생성한다. 서비스워커의 오프라인 최초 진입·버전 갱신·외부 RSS 캐시 동작은 실기기와 별도 환경에서 검증한다.

개발용 목업에는 가상 연락처·고정 접수 결과·무료 문구가 있다. `mockup/`과 `test/`는 운영 배포 산출물에서 제외하는 구성이 적절하다. 크롤링 제외만으로 파일이 비공개가 되지는 않는다.
