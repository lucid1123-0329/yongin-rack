# v71 운영 전환 기록

사용자가 커밋·푸시·운영 배포 진행을 승인했다. v70 화면은 유지하며, 소유자 전용 배포 전 데이터 백업 함수를 추가해 캐시 버전을 v71로 올렸다.

## 준비 및 변경

- 운영 v60와 편집기 HEAD 소스는 저장소 외부에 각각 백업했다. 두 소스는 동일하며 기존 코드 기준과도 일치한다.
- 서버 소스 두 파일을 편집기에 업로드했다. 웹 앱 운영 배포 번호는 이 단계에서 바꾸지 않았다.
- `backupBeforeSecurityRelease`: 소유자 Drive에 시트 사본과 스크립트 속성 JSON을 만든다. 새 PIN 입력용 `ADMIN_INITIAL_PIN`은 JSON에서 제외한다. 일반 웹 API 액션으로 노출하지 않는다.
- `initializeAdminPin`: 사용자가 스크립트 속성에 입력한 PIN을 적용하고 원문 입력 속성을 삭제한다.
- 자동 실행 API에서 NOT_FOUND 오류가 발생하여 두 함수는 소유자가 편집기에서 실행하도록 안내했다. 실패한 API 호출을 실행 완료로 간주하지 않았다.
- 과거 Git 추적 대상이던 Cloudflare 토큰 파일은 추적 해제했다. 로컬 파일은 유지한다. Git 원격 URL의 인증 토큰도 앞선 단계에서 제거했다. **기존 커밋의 토큰은 별도 폐기·재발급해야 한다. 이 작업은 기록을 재작성하거나 토큰을 폐기하지 않는다.**
- `verify-no-secrets.mjs`는 커밋 후보와 배포 준비 단계에서 알려진 토큰/비밀 파일 패턴을 검사하며 값은 출력하지 않는다. 모든 비밀을 검출하는 도구는 아니다.
- `publish-pages.yml`은 main에서 수동 실행할 때만 배포한다. 커밋/푸시만으로 실행하지 않는다. 서버 준비 확인값이 참이어야 한다.
- 홈페이지 배포물은 허용된 site 파일만 포함한다. 서버 소스, 목업, 테스트, 문서, 자격증명 파일은 Pages 배포물에 넣지 않는다.

## 전환 순서

1. 전체 테스트 및 비밀 파일 검사 통과 후 작업 브랜치 커밋/푸시.
2. 사용자 편집기에서 데이터 백업 및 새 PIN 초기화 완료 확인.
3. GitHub Pages 소스를 기존 main 루트 방식에서 Actions 방식으로 전환. 기존 사이트가 새 배포 전까지 유지되는지 확인.
4. main을 검토된 커밋으로 fast-forward. 다른 원격 변경이 있으면 강제 푸시하지 않는다.
5. 새 GAS 버전을 생성하고 현재 운영 배포 ID를 갱신해 URL 유지.
6. 익명 관리자 조회 차단과 새 인증 준비를 확인. 응답에 민감 데이터가 있으면 출력하지 않고 실패로 기록.
7. Pages 수동 배포 실행, 완료 후 실제 도메인 버전 및 핵심 화면 확인.
8. 사용자 로그인·실제 기기 알림 등록/수신, 키 재발급, 기존 취약 배포 폐기를 후속 확인.

## 운영 적용 결과 — 2026-09-17

- 사용자가 편집기에서 백업 및 PIN 초기화 두 함수 실행 완료를 확인했다. 백업 파일 내용은 별도로 열람하지 않았다.
- 적용 커밋: `272a2ccc548db11e31acdf9a9a57c8602198c736` (main 및 design/v2-reskin에 푸시).
- GAS 버전 61을 생성하여 기존 운영 웹 앱 배포 ID에 적용했다. API URL은 유지했다.
- 운영 API 점검: 공개 설정의 `pinConfigured: true`와 허용 필드만 반환됨을 확인했다. 익명 getSettings/getEstimates/getRequests는 모두 UNAUTHORIZED로 차단됐다. 응답의 실제 설정값과 고객 데이터는 로그에 출력하지 않았다.
- GitHub Actions `Publish reviewed site` 실행 35183981822: 빌드·자동 검증·배포 성공. https://github.com/lucid1123-0329/yongin-rack/actions/runs/35183981822
- 실제 HTTPS 도메인의 version.json은 71, 루트는 새 랜딩, /app/index.html은 v71 자산 참조를 반환했다.
- /Code.gs, /appsscript.json, /test/security.test.mjs는 모두 HTTP 404임을 확인했다.
- 브라우저에서 운영 랜딩 및 관리자 이동 후 PIN 입력 화면 표시를 확인했다. PIN을 알거나 대신 입력하지 않았으므로 실제 로그인·저장·고객 공유·실기기 푸시는 미검증이다.
- 남은 작업: 사용자 새 PIN 로그인 확인, 실기기 알림 확인, 과거 노출 키·토큰 폐기/재발급, 과거 배포 진입점 검토. 보안 조치 전체가 완료된 것으로 간주하지 않는다.
